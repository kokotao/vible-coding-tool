# npm 包防反编译与发布加固实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在不改变现有 `npm publish` 主流程的前提下，完成“源码最小暴露 + 逆向门槛提升 + 许可证约束 + 发布验收”的可执行闭环。

**Architecture:** 采用“分层保护”策略：发布包层（只发必要产物）+ 构建产物层（压缩/混淆/去 map）+ 业务架构层（核心逻辑服务端化）+ 合规层（License 与告警）。保留现有 `prepack -> build`、`prepublishOnly -> publish:check` 链路，只做增量脚本与配置改造。

**Tech Stack:** Node.js、TypeScript、Terser/javascript-obfuscator（二选一或组合）、npm scripts、现有 `publish-safety-check.cjs`。

---

## 0. 范围与原则（先对齐）

- 范围内：公开 npm 包的“反编译门槛提升”。
- 范围外：承诺“不可反编译”（技术上不可达）。
- 成功标准：
  - npm tarball 不包含 `src/`、测试、文档、`.env`、`*.map`。
  - 发布产物可运行、CLI 可用。
  - 核心敏感逻辑不以可读源码形式暴露。
  - 出现异常可在 5 分钟内回滚到当前发布方式。

---

## 1. 分阶段实施（推荐顺序）

### 阶段 A（当天可落地，低风险）

目标：先封住“最容易泄露源码”的口子。

改动点：
- 仅发布编译结果与运行必需资源（保持现有 `files` 白名单思路）。
- 强化 `publish:check`：新增对 `*.map`、`src/**`、`tests/**`、`docs/**` 的硬拦截。
- 构建时关闭 source map（若后续工具默认生成，统一删 map）。

验收：
- `npm pack --dry-run --json` 中无源码与 map 文件。
- `npm run build`、`npm run publish:check` 通过。
- 本地 `npm link` 后 `viblect --help` 正常。

### 阶段 B（1-2 天，收益最高）

目标：在不影响运行的前提下提升逆向成本。

改动点：
- 在 `build` 后增加 `build:protect`：对 `dist/src/**/*.js` 做压缩（Terser）或混淆（javascript-obfuscator）。
- 针对入口文件保留函数名/类名白名单，避免 CLI 启动异常。
- 新增 `verify:runtime` 脚本：启动健康检查 + 最小 CLI 命令回归。

验收：
- 产物可执行，`/health` 正常。
- 相同功能下，dist 可读性显著下降（人工抽检 3 个核心文件）。
- 构建耗时可接受（目标增加 < 30%）。

### 阶段 C（按需，中风险高收益）

目标：把最敏感逻辑从 npm 包迁走。

改动点：
- 将“密钥策略、核心业务规则、可被复用的判定算法”迁移到服务端 API。
- npm 包保留调用协议与最小执行壳。
- 增加失败兜底：网络失败时只返回受控错误，不泄露规则细节。

验收：
- 客户端包内不再包含核心策略实现。
- 抓包可见接口调用但不可见完整策略细节。

## 2. 你当前仓库的具体改造清单

优先文件：
- `package.json`
- `scripts/publish-safety-check.cjs`
- `README.md`（发布说明补充）
- （可选新增）`scripts/protect-dist.cjs`
- （可选新增）`scripts/verify-runtime.cjs`

建议脚本编排（保持原主链路）：
- `prepack`: `npm run build && npm run build:protect && npm run publish:check`
- `prepublishOnly`: 保留 `npm run publish:check`
- `build:protect`: 新增（压缩/混淆）
- `verify:runtime`: 新增（运行态最小回归）

说明：
- 不改你现有 `publish:check` 入口名称，避免影响既有习惯。
- 先以压缩为主，再渐进加混淆；混淆参数过激会影响可维护性与兼容性。

## 3. 安全与法律双保险

- 技术侧：混淆/压缩/去 map/最小发布面。
- 合规侧：
  - 明确 `LICENSE` 与“禁止未授权二次分发/逆向利用”条款（以法务模板为准）。
  - 关键输出增加可追踪水印（版本号、租户标识、时间戳等可配置元信息）。

---

## 4. 回滚与风险控制

主要风险：
- 混淆导致运行异常。
- 调试困难增加。
- 体积或启动耗时上升。

回滚预案（5分钟）：
1. `package.json` 将 `prepack` 恢复为仅 `npm run build`。
2. 移除 `build:protect` 调用。
3. 保留 `publish:check` 防泄露检查继续生效。
4. 重新 `npm pack --dry-run` 验证后再发布。

---

## 5. 验证清单（发布前必跑）

1. `npm run build`
2. `npm run build:protect`（若已接入）
3. `npm run publish:check`
4. `npm pack --dry-run --json`
5. `npm link && viblect --help`
6. `npm run dev` 后访问 `http://127.0.0.1:3000/health`

通过标准：以上命令全部成功，且打包清单不含源码与 map 文件。

---

## 6. 执行优先级建议

1. 先做阶段 A（当天完成，立刻降风险）。
2. 再做阶段 B（压缩优先，混淆渐进）。
3. 最后评估阶段 C（仅迁核心敏感逻辑）。
