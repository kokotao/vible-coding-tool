# 双向编程代理网关 MVP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 交付一个可运行的 `Node.js + TypeScript` 单体网关，打通“飞书消息 -> 风控与路由 -> Codex 会话 -> 飞书状态回推”的 MVP 主链路。

**Architecture:** 采用单体 Fastify 服务，内部按 `adapter / domain / storage / api` 分层。飞书入口、风险确认、会话路由、Codex 适配器和状态回推都通过统一的 `dispatch` 流程收敛，持久化使用 SQLite，首期用接口化的 `CodexAdapter` 预留多工具扩展。

**Tech Stack:** `Node.js 20+`, `TypeScript`, `Fastify`, `Zod`, `better-sqlite3`, `Vitest`, `tsx`, `pino`, `@larksuiteoapi/node-sdk`, `lark-cli` (dev only)

## 约束与实现口径

- 首期只接飞书和 Codex，但所有网关内部对象都保留 `platform`、`toolProvider` 字段。
- 所有机器人消息必须显式包含 `#session:<id>`，不做模糊猜测。
- 高风险确认只能由原消息发送人或管理员确认。
- 飞书普通消息和卡片确认都必须经过同一套幂等仓储。
- `CodexAdapter` 必须先定义接口，再提供 `http` 和 `mock` 两个实现。
- 默认坚持 TDD：先写失败测试，再实现最小代码，再跑通过。

## 飞书实现策略

- 正式实现使用 `@larksuiteoapi/node-sdk` 处理消息接收、事件分发、消息发送和卡片回调。
- `lark-cli` 仅用于开发调试，不进入生产依赖，不作为应用运行时能力来源。
- 本地开发优先验证：
  - `im.message.receive_v1` 事件是否可接收
  - 文本消息发送是否正常
  - 卡片确认回调是否能正确命中 `/api/feishu/webhook` 或风险确认路由
- 若本地公网回调受限，优先使用飞书事件 `WebSocket` 长连接做消息接收；卡片确认仍保留 webhook 实现。

export function parseSessionCommand(content: string) {
  const match = content.match(/#session:([a-zA-Z0-9_-]+)/);
  if (!match) throw new AppError("SESSION_REQUIRED", 400);
  return { sessionId: match[1], prompt: content.replace(match[0], "").trim() };
}

- 飞书 webhook 验签通过后能正确标准化消息并提取 `#session:<id>`。

- `npm run test` 与 `npm run build` 全部通过。
- `lark-cli` 可以独立完成飞书消息 smoke test，用于区分平台权限问题和业务代码问题。
