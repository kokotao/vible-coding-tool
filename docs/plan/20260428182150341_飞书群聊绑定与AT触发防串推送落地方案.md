# 飞书群聊绑定与AT触发防串推送落地方案

## 1. 目标与边界

### 目标
1. 群聊里只有被 `@机器人` 的消息才会进入执行链路。
2. 每条任务的回推都回到触发它的原群聊，不串到其他群或私聊。
3. 指令消息、任务状态、卡片操作的路由一一对应，可审计、可追溯。

### 非目标
1. 不改现有风险识别与确认策略。
2. 不改 Codex 执行器本身，仅改网关入站解析、路由绑定与出站发送。

## 2. 现状问题（基于当前代码）
1. 入站仅解析 `senderId + text`，未使用 `chat_id/chat_type/mentions` 做群聊 AT 门禁。
2. 回推主路径以 `recipientOpenId` 为主，群聊上下文未被持久化；并发群聊时存在串对象风险。
3. 全局 watcher 在未显式传 `recipientOpenId` 时会回退“最近 open_id”，在多群场景风险更高。
4. `callbackUrl` webhook 模式是固定目标，无法按会话精确路由到不同群。

## 3. 方案总览（Fail-Closed）

### 核心原则
1. 入站强校验：群聊消息未 `@机器人` 直接忽略（`ignored: group_not_mentioned`）。
2. 路由强绑定：首次有效指令建立 `session -> route` 绑定，后续状态回推必须命中该绑定。
3. 出站强约束：有群聊路由则仅允许 `chat_id` 发送；无路由不降级“最近 open_id”，直接跳过并记录审计。

### 推荐发送模式
1. 群聊路由统一走 Feishu OpenAPI：`/im/v1/messages?receive_id_type=chat_id`。
2. 私聊仍走 `open_id`。
3. 若仍配置为 webhook-only（固定 callbackUrl），群聊模式标记 `unsupported_routing_mode` 并在连接中心告警。

## 4. 数据模型改造

### 新增表
`feishu_session_routes`（建议）
- `session_id` TEXT UNIQUE
- `source_platform` TEXT（固定 `feishu`）
- `chat_type` TEXT（`p2p|group`）
- `chat_id` TEXT NULL
- `sender_open_id` TEXT NOT NULL
- `last_platform_message_id` TEXT NULL
- `route_status` TEXT（`active|invalid`）
- `created_at` TEXT
- `updated_at` TEXT

### 现有表扩展
`messages` 新增列（用于审计与回放）
- `chat_id` TEXT NULL
- `chat_type` TEXT NULL
- `mentioned_bot` INTEGER DEFAULT 0

说明：保持业务主键和既有映射不变，仅补路由审计维度。

- 创建任务时同步写入/刷新 `session route`。
- 会话复用从“按 sender 最近 session”升级为“按 sender+chat_id 最近 session（群聊）”。

3. `src/modules/feishu/feishu-message-parser.ts`
- 补 `stripFeishuMentionPrefix` 的结构化 mention 兼容（文本前缀 + mentions 数组双判定）。

### C. 出站发送与防串
1. `src/modules/notifications/feishu-outbound-notifier.ts`

- 禁止默认“最近 open_id”回退用于群聊任务。

### D. WS桥接补全
1. `src/modules/feishu/feishu-ws-bridge.ts`
- 透传 `chat_id/chat_type/mentions`，与 webhook 模式字段对齐。

## 6. 验收标准（必须全部通过）
1. 群聊未 `@机器人`：网关返回 `accepted=true, ignored=true, reason=group_not_mentioned`，不建任务。
2. 群聊已 `@机器人`：创建任务并建立 `session route(chat_id=当前群)`。
3. 同一用户在 A/B 两个群分别下发任务：A 的完成通知只到 A，B 只到 B。
4. 私聊场景不回归：仍按 `open_id` 正常收发。
5. 网页轻操作（停止/重试/确认）触发的消息仍回原群。
6. watcher 上报完成事件时，不再因“最近 open_id”导致串推。
7. 审计日志可追踪：每条通知都能看到 `sessionId -> route -> receive_id_type -> receive_id`。

1. 先发数据库迁移与后端代码。

### 回滚策略

2. 紧急回滚时仅关闭 strict 开关，不回滚库结构。
