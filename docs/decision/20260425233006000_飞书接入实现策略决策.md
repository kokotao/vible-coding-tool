# 飞书接入实现策略决策

## 背景

当前项目需要在首期打通飞书机器人与 Codex 网关的双向链路。调研后确认可选路径包括：

- 直接使用官方 Node SDK 作为业务实现基础
- 依赖 `lark-cli` 快速完成消息发送和联调
- 开发期通过 WebSocket 长连接接收事件，减少本地公网回调依赖

## 决策

- 正式运行时接入统一采用 `@larksuiteoapi/node-sdk`
- `lark-cli` 仅作为开发调试、权限验证和 smoke test 工具
- 本地开发优先采用 `WebSocket + webhook` 混合模式

## 具体说明

- Node SDK 负责：
  - 飞书消息接收
  - 消息发送
  - 卡片确认与回调适配
  - 事件分发与标准化
- `lark-cli` 负责：
  - 应用授权状态检查
  - 快速发送测试消息
  - 定位是飞书权限问题还是网关实现问题
- `WebSocket + webhook` 混合模式：
  - 开发阶段优先尝试用 WebSocket 长连接接收飞书事件
  - 卡片确认与平台回调仍保留 webhook 实现
  - 生产环境统一由网关服务承接，不依赖 CLI 常驻

## 原因

- Node SDK 更适合作为长期维护的服务端依赖，便于封装适配层和测试。
- `lark-cli` 非常适合联调和排障，但不适合作为业务运行时的核心实现。
- 混合模式能降低本地开发门槛，同时不牺牲正式链路设计。

## 影响

- `package.json` 需引入 `@larksuiteoapi/node-sdk`
- 实施计划中飞书模块默认按 SDK 封装
- README 和调试流程会补充 `lark-cli` 的 smoke test 命令

## 回滚策略

- 若 WebSocket 事件接收不稳定，开发环境回退为纯 webhook 模式
- 若 SDK 某能力不满足需求，再在适配层内部补 HTTP 直连，不影响上层业务接口
