# 双向编程代理网关正式设计（MVP）

## 0. 已确认范围

- 首期工具端：`Codex`
- 首期 IM 端：`飞书`
- 首期技术栈：`Node.js + TypeScript`
- 首期存储：`SQLite`
- 飞书安全：`HMAC-SHA256` 验签
- 交互模式：`双向交互`
- 会话路由：显式 `#session:<id>`
- 风控策略：仅高风险二次确认
- 高风险确认人：原消息发送人或管理员

## 1. 目标与非目标

### 1.1 目标
- 在 `vibe coding 工具（Codex/Claude）` 与 `飞书/QQ 机器人` 之间建立双向消息桥。
- 机器人可发送自然语言指令到开发工具执行。
- 开发工具执行过程与结果可回推到机器人。
- 使用显式会话路由：消息中通过 `#session:<id>` 定位目标会话。
- 风险控制采用“仅高风险二次确认”。

### 1.2 非目标（MVP 不做）
- 不做复杂多租户计费系统。
- 不做跨平台完整统一权限中心。
- 不做图形化编排控制台（仅保留后续扩展点）。
- 不做多工具并发编排。

## 2. 总体架构

```text
飞书Bot
   <-> Feishu Adapter
   <-> Central Gateway
   <-> Codex Adapter
   <-> Codex Session Runtime

Central Gateway 内部：
- Ingress API
- Session Router
- Risk Guard
- Command Dispatcher
- Event Store
- Notification Fanout
```

### 2.1 模块职责
- Feishu Adapter：接收/发送飞书协议，完成验签、事件解析、消息回复、卡片确认。
- Codex Adapter：对接 Codex 会话发送、状态拉取、结果订阅。
- Session Router：解析 `#session:<id>` 并路由到目标工具会话。
- Risk Guard：高风险动作识别，触发二次确认。
- Command Dispatcher：下发指令并维护任务状态机。
- Event Store：持久化消息、状态、审计日志。
- Notification Fanout：把状态更新回推到对应机器人会话。

### 2.2 运行原则

- 机器人侧承担控制面，负责发起、确认、查询和接收结果。
- Codex 侧承担执行面，负责消费自然语言任务并回传执行事件。
- Gateway 承担状态面、安全面和路由面，所有消息必须先标准化再执行。
- 首期以单体服务部署，后续若接入更多机器人或工具，再按适配器维度拆分。

### 2.3 飞书接入策略

- 正式运行时实现采用 `@larksuiteoapi/node-sdk`，由网关服务统一承接飞书消息、回调和消息发送。
- `lark-cli` 仅作为开发调试和联调工具，不作为网关运行时依赖。
- 开发阶段优先采用 `WebSocket + webhook` 混合模式：
  - 事件订阅、消息接收可优先尝试 `WebSocket` 长连接，降低本地开发对公网回调的依赖。
  - 卡片确认和需要平台回调的交互仍按 `webhook` 路径设计和落地。
- 生产环境统一由网关服务对接飞书，不依赖 CLI 常驻。

## 3. 核心流程

### 3.1 机器人 -> 开发工具（下达指令）
1. 用户在飞书发送消息：`#session:abc123 请修复 xxx 并提交测试结果`。
2. Feishu Adapter 验签、解析平台元数据并转成统一事件。
3. Session Router 提取 `session_id=abc123`。
4. Risk Guard 识别是否高风险：
   - 若否：直接分发执行。
   - 若是：返回“请确认执行”卡片，确认后再执行。
5. Codex Adapter 把自然语言消息投递到目标会话。
6. 网关回传“已受理/执行中/已完成/失败”状态到机器人。

### 3.2 开发工具 -> 机器人（回推结果）
1. Codex Adapter 订阅任务事件（开始、进度、输出、结束）。
2. Gateway 统一封装并写入 Event Store。
3. Notification Fanout 按原消息来源映射回飞书会话。
4. 机器人端展示可读摘要 + 关键日志链接（或片段）。

## 4. 会话与协议设计

### 4.1 消息规范（机器人侧）
- 必填：`#session:<id>`
- 正文：自然语言指令。
- 可选：`#tool:codex|claude`（首期默认 `codex`，为后续扩展预留）。

支持的首期消息类别：

- 普通指令：`#session:sess_001 帮我修复登录接口 500 问题`
- 查询状态：`#session:sess_001 当前进度如何`
- 控制命令：`#session:sess_001 停止当前任务`

### 4.2 网关内部统一事件结构（建议）
```json
{
  "event_id": "uuid",
  "source": "feishu|qq|codex|claude",
  "direction": "bot_to_tool|tool_to_bot",
  "session_id": "abc123",
  "message_id": "platform_msg_id",
  "user_id": "sender_id",
  "message_type": "command|query|control|tool_event",
  "content": "自然语言内容",
  "risk_level": "low|high",
  "status": "received|pending_confirm|running|success|failed|cancelled|interrupted",
  "reply_to_message_id": "optional_platform_msg_id",
  "timestamp": "2026-04-25T22:00:00+08:00"
}
```

### 4.3 会话模型

- `session_id` 是 Codex 执行会话的业务主键，不等同于飞书会话 ID。
- 一个 `session_id` 绑定一个主工具实例，首期固定绑定 `Codex`。
- 同一飞书群内的不同用户，只要带相同 `#session:<id>` 即可向同一 Codex 会话发送消息。
- 后续接入 `Claude` 时，只扩展 `session -> tool_provider` 映射，不改消息协议。

建议的会话状态：

- `idle`
- `running`
- `waiting_confirm`
- `failed`
- `closed`

## 5. 高风险二次确认策略

### 5.1 高风险识别（首版规则）
- 命令包含：`删除`、`重置`、`清库`、`覆盖发布`、`批量修改生产配置`、`强制推送` 等关键词。
- 或命中受保护目标：`prod`、`main/master`、关键配置目录。

### 5.2 确认机制
- 生成确认卡片：摘要 + 风险原因 + `确认执行/取消` 按钮。
- 确认有效期（建议）：120 秒。
- 超时默认取消，并回推“已取消（超时）”。
- 仅允许原消息发送人或管理员确认，避免群内他人误代确认。

### 5.3 幂等约束

- 飞书普通消息入口与卡片确认入口必须共用同一套幂等键策略。
- 重复回调、重复点击、飞书重试投递只能让第一次成功写入或推进状态。
- 幂等冲突时返回“已处理”而非重复执行。

## 6. 数据存储（MVP 最小集）
- `tool_sessions`：维护 `session_id -> tool_provider -> tool_session_ref` 的映射与状态。
- `messages`：保存机器人消息、工具回传消息以及标准化事件内容。
- `tasks`：维护一次自然语言执行请求的状态、摘要和生命周期。
- `risk_confirmations`：高风险确认记录、确认人、有效期、确认结果。
- `audit_logs`：全链路审计。

建议关键字段：

- `tool_sessions`
  - `id`, `session_id`, `tool_provider`, `tool_session_ref`, `status`, `created_by`, `created_at`, `updated_at`
- `messages`
  - `id`, `event_id`, `session_id`, `direction`, `source_platform`, `platform_message_id`, `sender_id`, `content`, `message_type`, `risk_level`, `status`, `created_at`
- `tasks`
  - `id`, `task_id`, `session_id`, `trigger_message_id`, `task_type`, `status`, `summary`, `started_at`, `finished_at`
- `risk_confirmations`
  - `id`, `task_id`, `session_id`, `requested_by`, `confirmation_token`, `status`, `expired_at`, `confirmed_by`, `confirmed_at`
- `audit_logs`
  - `id`, `event_id`, `session_id`, `action`, `actor_id`, `result`, `detail`, `created_at`

## 7. API 边界

- `POST /api/feishu/webhook`
  - 飞书事件入口，负责验签、消息接收、卡片回调
- `POST /api/messages/dispatch`
  - 网关内部统一分发入口，把标准消息送入路由和风控
- `POST /api/risk/confirm/:token`
  - 高风险确认入口，卡片点击后触发
- `POST /api/tool/codex/events`
  - Codex 侧事件回推入口，接收执行进度和结果
- `GET /api/sessions/:sessionId`
  - 查询会话状态
- `GET /api/tasks/:taskId`
  - 查询任务详情

实现约束：

- 平台入口 API 与内部业务 API 分开，避免后续接 QQ 时耦合飞书逻辑。
- `Codex Adapter` 必须先抽象接口层，至少暴露 `sendMessage`、`queryStatus`、`cancelTask`、`subscribeEvents`，方便后续接入 `Claude`。
- 飞书适配层优先基于官方 Node SDK 封装，不直接以 CLI 作为业务适配实现。

## 8. 错误处理与可观测

核心错误处理：

- 会话不存在：回复“未找到 session，请检查 `#session:<id>` 是否正确”，且不创建执行任务。
- 会话存在但 Codex 不可用：任务记为 `failed`，并回推“Codex 连接不可用，请稍后重试”。
- 高风险确认超时：状态记为 `cancelled`，审计记录 `confirm_timeout`。
- 工具执行中断：状态记为 `failed` 或 `interrupted`，回推最近一次执行进度。
- 重复回调或重复点击：命中幂等保护，只允许第一次生效。

可观测要求：

- 指标：请求量、路由成功率、执行成功率、确认超时率、平均响应时延。
- 日志：按 `event_id/session_id` 可串联追踪。
- 告警：网关不可用、适配器断连、失败率突增。

## 9. MVP 验收标准
- 能从飞书发送 `#session:<id>` 指令并成功触发 Codex 会话执行。
- 能把执行状态（至少 running/success/failed）回推到飞书。
- 高风险指令会触发二次确认，未确认不得执行。
- 高风险确认只能由原消息发送人或管理员生效。
- 重复点击确认不会重复执行任务。
- SQLite 中能查到 `tool_sessions/messages/tasks/risk_confirmations/audit_logs`。
- 任一失败链路都有明确错误提示，不出现静默失败。

## 10. 里程碑建议
- M1：飞书双向链路 + 风险确认 + 基础审计。
- M2：QQ 适配器 + 统一状态回推模板。
- M3：策略中心（可配置风险规则）+ 稳定性增强。

## 11. 风险与回滚
- 风险：自然语言全开放带来误触发风险。
- 控制：高风险确认 + 审计留痕 + 操作回放。
- 回滚：可按 `task_id` 执行补偿动作（MVP 先支持人工回滚 SOP）。

## 12. 网页管理台设计（首版）

### 12.1 产品定位

- 飞书 / QQ 机器人对话消息是主交互面，负责发起任务、查看结果和处理大部分确认。
- 网页管理台是辅助信息面和轻操作面，负责展示全局状态、任务、会话、风控与审计，并承接少量补位操作。
- 首版网页端不作为任务发起主入口，也不承载完整人工介入流程。

### 12.2 首页信息架构

首页默认主视图采用综合总览，结构如下：

- 顶部指标卡：
  - `运行中任务数`
  - `待确认风险数`
  - `活跃会话数`
  - `今日失败任务数`
- 中间上半区：`任务时间线流`
- 中间下半区：`最近活跃会话简洁列表`
- 右侧上半区：`风险待确认`
- 右侧下半区：`连接中心`

设计约束：

- 右侧优先显示 `风险待确认`，把必须处理的风险动作放在更高视觉优先级。
- 首页详情入口支持两类：
  - 点击任务时间线项进入任务详情
  - 点击会话列表进入详情
- 详情页的信息组织默认以任务详情为主，再关联所属 `session`

### 12.3 首页模块展示规则

- `任务时间线流`
  - 以时间线方式展示当前和最近任务事件，强调运行状态变化
  - 不使用普通表格作为首页主形态
- `最近活跃会话`
  - 使用简洁列表
  - 展示优先级为：`任务标题为主，sessionId 为辅`
  - 如果无法获取 Codex 当前任务标题，则回退为 `sessionId`
- `风险待确认`
  - 首页卡片内支持直接确认 / 取消
  - 但机器人对话消息仍然是主确认链路，网页端确认是补充入口

### 12.4 连接中心

- 首页右侧连接中心为操作型区域，不只是状态展示
- 编辑方式采用抽屉
- 抽屉结构采用顶部 Tab，包含 4 个配置面：
  - `连接`
  - `风控`
  - `模板`
  - `绑定`

各 Tab 首版范围：

- `连接`
  - `App ID / Secret`
  - 接入模式
  - 测试连接
  - 保存
  - 事件订阅状态
  - 权限检查
  - 回调地址
  - 最近一次联调结果
- `风控`
  - 高风险关键词
  - 确认策略
  - 与确认超时相关的基础规则
- `模板`
  - 仅配置消息文案模板
  - 首版覆盖：`任务开始 / 成功 / 失败 / 待确认`
- `绑定`
  - 默认群 / 频道绑定
  - `session` 前缀规则

首版配置作用域：

- 全局单配置
- `session` 首版按机器人类型前缀生成，例如 `feishu-codex-0001`

### 12.5 任务详情页

任务详情页首版包含 4 个核心区块：

- `任务摘要`
- `消息时间线`
- `风控记录`
- `审计日志`

其中 `消息时间线` 采用半展开级展示：

- 默认显示摘要节点
- 支持按节点展开查看原始内容
- 兼顾可读性与排障能力

### 12.6 网页端轻操作边界

网页管理端首版允许以下轻操作：

- `停止任务`
- `重试通知`
- `重新测试连接`
- `补做确认`

首版不做以下能力：

- 不把网页端作为大多数任务的主发起入口
- 不在网页端承载完整消息重放与全过程人工介入
- 不在首页引入复杂路由规则引擎
